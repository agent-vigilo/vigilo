# Agent Credentials

A run profile names a credential; the worker resolves its value through trusted
operator configuration immediately before invoking the agent. The reference is
stored with the run. Resolved values are not added to profiles, queue messages,
request bodies, or evaluator inputs by the host.

```yaml
agent:
  provider: custom
  name: support-agent
  http:
    url: https://agent.example.com/evaluate
    credential: agent-api
```

References contain 1–128 ASCII letters, digits, dots, underscores, or hyphens.
A reference is a lookup name, not permission to access a secret. Profiles cannot
select secret files, environment variables, or credential-service URLs.

Start either worker mode with `--agent-credentials /etc/vigilo/credentials.json`
(or `VIGILO_AGENT_CREDENTIALS`). This JSON file is operator-owned and loaded once
at process startup. Only workers consume it. Missing provider configuration or an
unknown reference fails the invocation; there is no unauthenticated fallback.
Workers without credential references need no credential provider or external service.

## Standalone bindings

```json
{
  "version": 1,
  "provider": {
    "type": "local",
    "bindings": {
      "agent-api": {
        "source": { "type": "env", "name": "AGENT_API_TOKEN" },
        "allowed_origin": "https://agent.example.com",
        "header": "Authorization",
        "prefix": "Bearer "
      }
    }
  }
}
```

Supply `AGENT_API_TOKEN` through your process manager. For a mounted secret, replace
`source` with `{"type":"file","path":"/run/secrets/agent-token"}`. Files contain
exact UTF-8 secret values: trailing newlines are not trimmed. Paths are interpreted
relative to the worker's working directory; absolute paths avoid ambiguity. Projected
secret symlinks are supported; their targets must be regular files.

The worker validates the reference, origin, and header conflicts before reading a
local secret. Origins match scheme, host, and effective port; they cannot contain
paths other than `/`, queries, userinfo, or fragments. All paths and HTTP methods on the configured
origin share a local binding's authority. Use separate origins when paths have different
trust levels. Bindings are appropriate for an operator-controlled trust domain;
a shared worker's local bindings do not provide tenant isolation.

Secret sources are read on every attempt, without caching. Atomically replacing a
secret file affects subsequent resolutions; changing a process environment requires
restarting the worker. Run configuration freezes the reference, not the secret value.

## Service provider

The core includes a client for this HTTP protocol. A separately operated service
owns authorization and secret retrieval; no hosted product or cloud SDK is required
by core. It can integrate with customer-owned secret stores behind this protocol.

```json
{
  "version": 1,
  "provider": {
    "type": "service",
    "endpoint": "https://credentials.internal.example.com/v1/resolve",
    "token": { "type": "file", "path": "/run/identity/credential-service-token" },
    "grants_directory": "/run/vigilo/grants"
  }
}
```

The operator provisions a service bearer token and a grant file named with the
canonical run UUID under `grants_directory`, such as
`/run/vigilo/grants/01900000-0000-7000-8000-000000000001`. The file contains the exact
opaque grant value. Both token and grant use the same bounded source handling as
local secrets. Core only reads these inputs; it does not create or delete credential
or grant files. The operator owns provisioning, rotation, and removal. The token can instead use an environment source. The service token
may be a workload-identity token issued by external infrastructure; core does not
perform cloud token exchange, validate that token's claims, or issue execution grants.

The worker sends one authenticated POST per credential-bearing invocation attempt:

```json
{
  "version": 1,
  "credential": "agent-api",
  "destination": "https://agent.example.com/evaluate",
  "run_id": "01900000-0000-7000-8000-000000000001",
  "execution_id": "01900000-0000-7000-8000-000000000002",
  "attempt_id": "01900000-0000-7000-8000-000000000003",
  "grant": "opaque-execution-grant"
}
```

IDs come from the allocated execution, not profile metadata. The service must verify
its bearer token's issuer, audience, expiry, and worker identity; then verify the
grant's scope/lifetime and the worker's assignment to that run/execution. IDs and a
credential name are not authorization evidence. Bind authorization to the requested
destination and organization. Two organizations can use the same credential name
without sharing a secret. The service must enforce that separation.

An authorized response is HTTP 200 with this exact JSON shape:

```json
{
  "version": 1,
  "allowed_origin": "https://agent.example.com",
  "header": "Authorization",
  "value": "Bearer resolved-token",
  "expires_at": "2030-01-01T00:01:00Z"
}
```

`value` is the complete header value, including its prefix. `expires_at` is an RFC
3339 timestamp in the future; the worker checks it again before sending the agent
request. The service should choose short validity appropriate to the credential.
Core validates the response version, origin, header, size, and expiry. It does not
cache the response or persist its fields. Core adds no control-database queries for credential resolution.
Revoking a grant prevents future resolution when enforced by the service; it does
not retract an already delivered token or cancel an in-flight agent request.

Timeouts, transport failures, and HTTP 408, 425, 429, 500, 502, 503, or 504 produce
retryable `credential_unavailable` failures using the existing durable attempt
budget/backoff. There are no provider-internal retries and resolver Retry-After is
not interpreted. Other non-200 statuses are terminal authentication failures.
Malformed, expired, oversized, or mismatched responses are terminal configuration
failures. Service response bodies never become error diagnostics. Service outages
never fall back to a different secret source or an unauthenticated agent call.

## Transport and exposure boundaries

Credential-bearing requests require HTTPS and use the bundled WebPKI TLS roots.
The provider does not configure custom certificate authorities or mutual TLS.
They disable redirects and ambient HTTP proxies for both resolver and agent calls.
For local development only, top-level `"allow_http_loopback": true` permits HTTP
with literal loopback IP addresses; it does not allow arbitrary HTTP hosts or the
hostname `localhost`. URL userinfo and fragments are rejected.

Headers may be `Authorization`, `api-key`, or `x-` headers, except `x-forwarded-*`
and `x-http-method-override`. `X-Vigilo-Attempt-Id` is also reserved for
host-generated correlation and cannot carry a credential. Static profile headers cannot override the managed
header (case-insensitive), Host, or transport/routing controls. Ordinary nonsecret
headers remain supported. Static headers are persisted, so never put secrets in them.

| Boundary | Limit |
| --- | --- |
| Operator configuration | 1 MiB; version 1; unknown fields rejected |
| Secret, service token, or grant | 16 KiB each |
| Combined authentication header value | 16 KiB |
| Resolver response | 64 KiB |
| Credential destination URL | 8,192 bytes |
| Concurrent resolutions per worker | 64 |
| Resolution deadline, including permit wait and source reads | 10 seconds |

Agent body limits and request timeout apply separately after resolution. Credentials
are marked sensitive in HTTP header diagnostics. Authenticated agent HTTP failures
omit response-body excerpts. Host diagnostics do not include secret values, source
contents, or credential-service response bodies.

An authorized worker and the intended endpoint receive the secret. This is not
protection against a compromised worker, memory dumps, or an endpoint echoing secrets
in successful responses. Responses still undergo normal evaluation and retention;
generic redaction cannot reliably detect transformed secrets. Core does not promise
complete memory erasure or zero disclosure. Operators must protect worker memory,
secret sources, grant files, service authentication, and endpoint behavior.
