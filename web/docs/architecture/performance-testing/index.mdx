# Performance Testing

Vigilo's <GlossaryTerm term="performance-harness">performance harness</GlossaryTerm>
is an external `xtask` package. Production Vigilo does not depend on the
harness, while the harness measures only supported CLI, database, RabbitMQ,
HTTP, and evaluator boundaries. Every
<GlossaryTerm term="measured-sample">measured sample</GlossaryTerm> must pass its
<GlossaryTerm term="exact-correctness-oracle">exact correctness oracle</GlossaryTerm>
before it can contribute to statistics.

A <GlossaryTerm term="performance-campaign">performance campaign</GlossaryTerm>
resolves one performance profile against one or two test subjects and verifies
each subject's <GlossaryTerm term="performance-build-manifest">build manifest</GlossaryTerm>
before execution.

## Component Boundaries

Versioned <GlossaryTerm term="performance-workload">performance workloads</GlossaryTerm>
exercise release-binary run creation, dispatch, HTTP agent, Wasm evaluation,
worker persistence, outbox publication, lease recovery, and run finalization.
<GlossaryTerm term="performance-profile">Performance profiles</GlossaryTerm>
select explicit <GlossaryTerm term="workload-tuple">workload tuples</GlossaryTerm>
around page, batch, and concurrency boundaries; the harness never expands
dimensions into a Cartesian product. Exact HTTP requests, worker deliveries,
and durable rows catch lost batching or
<GlossaryTerm term="amplification">amplification</GlossaryTerm> before timing is
interpreted.

Administration workloads cover cancellation fanout, terminal status/results,
JSON and JSONL export, shard move/rebalance, and coordinator placement scaling.
They use logical routes backed by isolated databases on one PostgreSQL server,
so route growth is measured without pretending to reproduce a database fleet.
Creation and HTTP variants also schedule the remaining page/group boundaries
and a larger response payload.

Each <GlossaryTerm term="component-scaling-model">component scaling model</GlossaryTerm>
uses either a sample-level fixed-cost-plus-slope fit or explicit stepped
estimates at known batch boundaries. Every
<GlossaryTerm term="model-point">model point</GlossaryTerm> requires repeated
valid samples, exact observations, and residuals within its registered
tolerance.

PostgreSQL normalized statements, planning time/counts, shared/temp buffers,
and WAL counters are captured after the timed process exits. The
`cargo perf diagnose` command renders them as
<GlossaryTerm term="performance-diagnostics">non-gating diagnostics</GlossaryTerm>.
Complete statement counters also separate control, execution, and shared
databases into read, DML, mixed, transaction, and other categories. These counters
include statements outside the diagnostic query ranking. `cargo perf check-queries`
checks every measured repetition against the campaign's frozen absolute statement
ceilings; missing or inconsistent evidence fails validation. Shared databases
retain combined attribution, and statement counts remain distinct from physical
row writes.
The model command writes the owned component-model artifact and fails closed on
incomplete or nonlinear evidence.

Before measurement, each campaign freezes its validated workload registry,
exact resolved profile, optional reviewed budget, and verified build manifests
inside the retained run directory. Calibration, projection, and confirmation
reload those run-relative contracts, so later repository edits cannot silently
change the meaning of existing evidence.

## Large-Data Contracts

Read and export fixtures contain 250 or 251 completed executions, evaluator
results, and deterministic diagnostics across one or two routes. Process
measurements record total output bytes, time to first and last stdout byte, and
peak RSS. JSONL is checked as streamed typed records with a 256 MiB fixture
limit; JSON is checked as one materialized document with a separate 512 MiB
tested limit.

Shard movement persists the actual rows, bytes, and completed page count for
each copied table. A lower bound derived from 1,000 rows or 4 MiB per page is
validated, but it is never substituted for the recorded distribution. The move
command is then replayed and must report the same verified target without moving
it again. Rebalance samples apply one claimed item per resumable pass, require
every persisted item to complete verification, and require every selected route
to point at the target. Database creation,
migrations, route registration, terminal fixture generation, and rebalance
planning occur before collector reset.

Criterion remains conditional on a legitimate production library surface.
Runtime and database modules are binary-private, so the release
executable remains the sole component measurement authority.

## Calibration Boundaries

- `calibration-v1` performs
  <GlossaryTerm term="noise-calibration">noise calibration</GlossaryTerm> by
  comparing one immutable build to itself in 30
  <GlossaryTerm term="counterbalanced-block">counterbalanced blocks</GlossaryTerm> for
  representative CPU, database, broker, Wasm, and end-to-end anchors.
- Noise analysis checks confidence bounds and residual orientation effects, then
  uses the 95% interval width and reviewed power target to recommend an even
  independent block count for each wall-time budget.
- `capacity-v1` is a single-build
  <GlossaryTerm term="capacity-staircase">capacity staircase</GlossaryTerm>. It
  remains separate from fixed-load A/B regression results and never claims
  maximum fleet capacity.
- A <GlossaryTerm term="worker-knee">worker knee</GlossaryTerm> may come from
  the throughput/latency rule or the reviewed normalized per-worker CPU ceiling.
- Shared PostgreSQL, RabbitMQ, agent, or host pressure invalidates a capacity
  point instead of being reported as Vigilo's worker knee.
- Publication requires matching build digests and immutable canonical evidence.
  It binds a reviewed <GlossaryTerm term="practical-performance-budget">performance
  budget</GlossaryTerm> into a versioned policy and
  <GlossaryTerm term="performance-baseline">`reference-v2` baseline candidate</GlossaryTerm>.

## Deployment Projection

`cargo perf project` creates a
<GlossaryTerm term="capacity-projection">capacity projection</GlossaryTerm> from
one completed bounded-capacity campaign and a versioned input under
`performance/deployments`. The input names peak and average traffic, evaluation
run and evaluator mix, payloads, retries, topology, utilization policy, and
usable dependency limits. Each limit retains its measurement, provider, or
operator provenance rather than being inferred from a missing value.

The projection jointly resamples all one/two-worker points and resource-demand
coefficients. Its report shows worker, CPU, memory, PostgreSQL, RabbitMQ, HTTP,
Wasm, storage, retry, and coordinator demand; formulas and 95% intervals remain
visible beside the limiting resource. Missing limits produce unknown overall
capacity. Material nonlinearity, shared dependency saturation, operationally
unbounded paths, and staging error beyond the declared tolerance prevent a
supported label.

Worker counts above the measured two-process range are directional scenarios,
not fleet measurements. A small staging observation records model error without
requiring maximum scale. The current coordinator broker publish/confirm path is
declared unbounded, so the checked-in planning example remains invalid until a
separately tested production deadline and settlement contract exists.

## Ingestion Measurements

The `ingestion-baseline-v1` profile measures initial run creation with bounded
case-count and payload-size sweeps plus dataset reuse. A reused-dataset sample
prepares its first run before measurement, then measures only the second run.
The exact oracle verifies stored payloads, membership, chunks, and zero premature
execution or dispatch.

Linux peak-memory samples use the child's high-water mark after the kernel
confirms it has executed. Spawn can return before that transition, while the
child still has the harness's inherited memory. Missing or malformed execution
state and missed memory samples remain unavailable rather than being accepted.

Samples separate SQL calls and returned rows from physical table-row insert,
update, and delete counts. Their external counters are captured before oracle
reads. The single PostgreSQL placement owns both control and execution metadata;
WAL is counted once for that server. Repeated-text input padding is compressible,
so database growth and WAL are interpreted alongside submitted bytes. Local
results are informative evidence rather than production capacity ratings.

## Stability And Recovery

Each long-running <GlossaryTerm term="reliability-run">reliability run</GlossaryTerm>
is separate from fixed-load comparisons.
The bounded soak holds one production coordinator and worker process open for
at least 30 minutes while small runs make useful progress at fixed observation
intervals. It gates exact terminal work, queue drain, process liveness, absolute
RSS, file-descriptor growth, retry/delivery amplification, and end-window
throughput retention. These safety limits do not become reviewed performance
budgets without repeated canonical evidence.

Controlled recovery uses the same isolated topology. It completes work before
a real run-owned RabbitMQ application restart, retains the resident processes,
then requires new useful work and a drained backlog within the registered
deadline. The machine artifact records the fault, recovery time, interval
observations, exact durable totals, and every failed condition. A deterministic
pure verdict fixture proves that leaks, stalls, lost work, early exits, and
missed recovery are not accepted when services are unavailable to unit tests.

Topology teardown inventories all containers, networks, and volumes by the exact
Compose project, including stopped containers, and validates their run,
performance, project, and component labels. Normal cleanup must match the
persisted inventory exactly. Startup rollback accepts only a bounded subset of
the fixed topology, and both paths prove that no project-owned or run-owned
resource remains.

## Verdict Flow

A comparison using a <GlossaryTerm term="gating-profile">gating profile</GlossaryTerm>
loads one exact budget for each workload tuple. Results from a different
environment ID, too few blocks, excessive orientation bias, or a failed
correctness oracle are non-green. A confidence interval within budget passes.
The first interval wholly beyond budget is inconclusive and requires one fixed
independent confirmation; only the second matching result is a regression.

## First Use

Run `cargo perf check`, create one
<GlossaryTerm term="performance-test-subject">immutable release snapshot</GlossaryTerm>,
and begin with the service-free `developer-v1` startup workload. When that
passes, run `pr-v1` against the same snapshot with Docker available. This
exercises the small real PostgreSQL, RabbitMQ, Ceph object-storage, HTTP-agent, Wasm, and lifecycle
paths before committing to a reference, capacity, recovery, or soak campaign.
Exact-oracle failures take priority over timing; `pr-v1` produces
<GlossaryTerm term="informative-timing">informative timing</GlossaryTerm> rather
than a regression verdict.

## Regression Verification

Performance measurements come from real release binaries and services after
exact correctness checks pass. Compare immutable baseline and candidate builds
on the exclusive canonical host under a published gating profile. An initial
over-budget interval is inconclusive until its fixed independent confirmation
also exceeds the budget. Outage and sustained-operation changes additionally
run the recovery or soak profile.

A passing comparison means no regression was detected at the published budget
and confidence. The command sequence is documented in the repository's
[`performance/README.md`](https://github.com/agent-vigilo/vigilo/blob/main/performance/README.md#regression-verification).

## Continuous Integration

Shared hosted CI runs service-free contracts and exact correctness checks, not
wall-clock gates. Canonical, nightly, and soak jobs are defined for an exclusive
self-hosted Linux runner but remain inert until repository variables enable the
runner and then its schedules. Manual runs are enabled separately so the host
can be validated before recurring work starts. Reports are appended to the job
summary and retained as bounded artifacts; no performance badge is claimed
before canonical repeatability exists. Activation requires an Actions runner
version `2.327.1` or newer for the workflow's Node 24 actions, the documented
runner labels, and repository variables; it requires no workflow edit.
Nightly capacity evidence runs without a deployment assumption. Setting
`VIGILO_PERF_DEPLOYMENT` to a reviewed checked-in input additionally enables its
projection; the intentionally invalid planning example is never scheduled by
default.
The comparison on the
<GlossaryTerm term="canonical-environment">canonical environment</GlossaryTerm>
defaults to informative `reference-v1`; after review,
`VIGILO_PERF_REFERENCE_PROFILE` selects a committed gating profile without a
workflow change.
