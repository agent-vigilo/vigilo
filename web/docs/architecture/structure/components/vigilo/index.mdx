# Vigilo Components

The library owns runtime implementation and database workflows. The CLI adapter
owns argument parsing, process logging, signal handling and output formatting.
`vigilo::operations::Client` exposes typed standalone status, cancellation and execution control without CLI parsing
or process setup. Its operator-supplied configuration creates shared lazy database
pools; the caller owns the Tokio runtime. Database models and pools remain private.

```rust
use vigilo::operations::{Client, Config};

async fn example() -> Result<(), Box<dyn std::error::Error>> {
let client = Client::new(Config::new(std::env::var("DATABASE_URL")?))?;
let run_id = "0198f36d-f7db-7d90-998c-d60d498dd979".parse()?;
let status = client.run_status(run_id).await?;
println!("{}", status.details.status);
Ok(())
}
```

The client assumes an authorized standalone operator. It does not authenticate
callers. Status reports progress source and completeness explicitly; observations
across databases are not one atomic snapshot. Missing runs and dependency failures
have typed errors. Dropping a status future cancels the read, not the run.

`Client::runs` binds operator-owned storage configuration to a shared run client.
`prepare_run` returns privately constructed verified work without authorizing
execution. `accept_run` commits acceptance of that exact work; `create_run` combines
the two for a trusted operator. `resume_creation` retries the same immutable inputs
and run ID. It is distinct from resuming paused execution. Dropping a request does
not undo committed preparation, acceptance or control changes.

The CLI uses the same typed operations for creation, cancellation and status/watch
output. Other commands and daemon adapters call private library workflows. Neither pools nor persistence
records are part of the public operation API.

## Fixed database bindings

`operations::DatabasePools` holds separate scheduler, execution and user pools
for each explicitly configured database. Clones share those pools; pool limits
apply per database and authority. `user_client()` reuses the user pools for typed
status reads. Raw SQL executors and credentials are not exposed to requests.

The trusted host supplies `DatabaseBindings` with a control alias and a
`DatabaseBinding` for every placement. Each binding declares its purpose, schema,
limited non-login function owner and three distinct `DatabaseCredential` logins.
Connection URIs include the host, database, username and password; TLS settings
are explicit URI options. These bindings reject ambient `PG*` connection overrides
and arbitrary startup options. Standalone `Client` configuration is separate.

Construction validates configuration without opening connections. Call `validate()`
before serving requests. Each new physical connection independently checks its
login, role memberships, table protections, function definitions and grants.
Scheduler logins have explicit access to the installed discovery and claim functions.
Narrow table grants support scoped follow-up work on the transaction retaining its
claim. Scheduler, user and execution work-table access requires row policies.
Deployment metadata is read-only. The host installs and tests policy semantics;
structural validation does not prove that an arbitrary policy is correct.

Validation uses bounded catalog reads at connection opening and explicit
revalidation, not per operation. Hosts revalidate or replace pools after permission
or installation changes. `close()` closes all shared clones and waits for borrowed
connections. The caller owns the Tokio runtime and shutdown lifecycle.

Dataset ingestion owns bounded preparation, immutable upload and generation-fenced
catalog publication. Operators or schedulers invoke resume and cleanup commands;
no coordinator claims a local input file. The storage adapter owns provider I/O
and exact key deletion, while PostgreSQL stores compact upload progress and
ownership. See [Dataset Ingestion](/docs/architecture/case-storage/ingestion).

Dataset-reference run preparation traverses verified batches through the storage
adapter, freezes chunk and gate membership, and seals compact control references.
Execution admission verifies compact local metadata before activation. The
foreground caller resumes preparation; coordinators recover requested admission
under the run creation lease. See
[Run Preparation](/docs/architecture/case-storage/run-preparation).

## Status read flow

Restricted database reads use fixed credential bindings and transaction-local
caller context. Connections are checked before serving reads; committing,
rolling back, or dropping the transaction clears its context. Routing groups
summary reads by database and never falls back to another credential binding.
The embedding host supplies trusted identity and installs database access policy.
