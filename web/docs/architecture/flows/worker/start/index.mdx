# Start

How `vigilo worker start` runs a long-lived worker consumer that processes chunk-ready broker messages until shutdown, reopening the broker consumer after transient RabbitMQ interruptions.

Chunk-ready broker messages carry `run_id`, `run_shard`, `chunk_id`,
`database_alias`, and `write_epoch`. The worker resolves the hinted pool and
claims the chunk only when the execution database accepts that epoch locally.
Stale hints are refreshed from control metadata; valid hints avoid a
control-database route lookup.

By default, one worker process keeps one chunk in flight at a time. Set `--max-inflight-chunks` or `VIGILO_WORKER_MAX_INFLIGHT_CHUNKS` to allow multiple chunk messages to be processed concurrently by the same process. RabbitMQ prefetch is set to the same value, so the worker only reserves chunk messages it has capacity to run.

Each worker process uses a stable `worker_id` for attempts it allocates. While processing a chunk, it renews the chunk lease and the running attempt leases; terminal transitions require the current attempt tokens and a live attempt lease for that worker.

Workers read assigned case batches through a shared, bounded immutable-byte cache
and fetch misses through the [storage adapter](/docs/architecture/case-storage/).
Every use verifies complete files and exact membership before execution evidence
is persisted in the routed database. [Run Preparation](/docs/architecture/case-storage/run-preparation)
describes cache ownership, limits and failure handling.
